路径为：查已提交ID → 读取历史 → 投影本次请求 → 一次应用层发送 → 检查取消/期限 → 验收完整纯文本 → 再检查 → 提交整轮。已有ID与同问题复用原答案；冲突问题发送前拒绝。追加写入失败后协调器不可继续使用，应重开日志恢复。

`FixtureReplyClient`只允许回环HTTP，显式`Proxy.NO_PROXY`，不读取密钥。它限制回复字节、严格UTF-8、关闭自动跳转并以固定长度流式写入。真实接收端记录用于核对丢失回复时的POST数量，而不是仅统计方法调用次数。有关流式语义参见[Java 8官方文档](https://docs.oracle.com/javase/8/docs/api/java/net/HttpURLConnection.html#setFixedLengthStreamingMode-int-)及[OpenJDK 8 HttpClient实现](https://github.com/openjdk/jdk8u/blob/master/jdk/src/share/classes/sun/net/www/http/HttpClient.java)。本次观察不推广为所有提供商的恰好一次保证。

## 实际运行与反例

最终协议`turn-flow-local-v3`，产物目录`demos/14-turn-flow/out/local-v4`。v1–v4是开发过程中的运行目录，不是独立统计样本。最终运行环境由manifest记录：Windows、Java 8u171、Python 3、Gson 2.10.1。

最终16个固定场景全部完成，实际接收13份回环HTTP请求。19条保存记录中，15条是预置历史，4条为协调器新增提交；不把预置记录当作新结果，不合并为成功率。逐场景结果及源码/产物指纹见[运行摘要](turn-flow-local-20261112.json)。

重点观察：

- 第二轮请求确实携带第一轮完整问答。
- 请求窗口移除最早一轮，文件仍保存那轮；投影不删除历史。
- 服务端已读完请求但未回复时，候选不入库，旧轮保留。没有据此推断远端未执行。
- 回复后、提交检查前取消：请求已发生，候选未提交。
- 同一JVM中关闭并重开日志后，同ID同问题不再发送；同ID另一问题拒绝。不是新的子进程崩溃试验。
- 非空但513个UTF-8字节的回答、畸形UTF-8、4097字节响应及空白回答均拒绝，旧历史保留。
- 503没有被自动套用只读重试循环。
- 受控单调时钟验证期限检查，不用于报告真实延迟；中断标记保留。
- 其他线程拒绝使用该协调器；关闭通道的实际IO错误使后续调用要求重开。不是磁盘断电测试，也不是多协调器共享日志的安全证明。

独立`audit.py`逐条解析HTTP记录、Base64日志帧、SHA256、完整问答与协议计数。篡改结果计数或追加请求后，即使同时更新manifest中的文件哈希，协议/日志检查仍拒绝；这些负例使用产物副本，未改原证据。源码修改后对旧运行使用`--verify-sources`会失败，最终v4与当前源码匹配。已有输出目录被拒绝，原manifest未改变。
