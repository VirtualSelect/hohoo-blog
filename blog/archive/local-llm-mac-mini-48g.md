在 48GB 统一内存里，模型权重、KV 缓存和运行时临时分配要共享同一份预算。只知道“27B、4-bit”，还不足以判断某个上下文长度能否稳定运行。

**阅读范围（2026-11-07 复核）：本文保留容量推导与配置讨论，不作为部署性能实测报告。** 当前仓库没有与这篇文章配套的完整模型标识、芯片型号、运行时版本、同条件吞吐记录及 OOM 日志，无法据此推荐特定量化包，或确认 MTP 的收益。原稿的“约 2GB 换 30%–50% 吞吐”“量化后几乎无损”等断言撤回。

## 1. 先算能算的，再测不能算的

27B 参数全部以 FP16 存储时，仅参数数据的理想容量为 27 × 10⁹ × 2 = **54GB**；全部按 4-bit 紧凑存储则为 **13.5GB**。它们都不是实际加载后的进程内存。

模型包可能混用不同精度，并带有量化元数据。实际预算还包括系统、激活、缓存和临时缓冲。先记录模型版本与量化格式，再测加载后的占用，比从文件名里的“Q4”推断速度或质量更可靠。

| 问题 | 可以先推导什么 | 必须补测什么 |
| --- | --- | --- |
| 权重能否装下 | 参数数 × 位宽的理想容量 | 实际模型包与加载峰值 |
| 上下文能开多长 | 由实际模型配置计算 KV 数据量 | prefill / decode 峰值、并发与错误日志 |
| 量化是否值得 | 理想存储量变化 | 同题回答质量、延迟与实际内存 |
| MTP 是否开启 | 先确认模型与运行时是否支持 | 同输入、同输出长度的开关对照 |

MTP 的收益和内存代价不能从模型总参数量推出。本文没有这组对照，因此不给默认开启建议。

## 2. KV 缓存：上下文真正的成本中心

自回归生成时，每个 token 的注意力 Key/Value 都要缓存，KV 缓存随上下文**线性**增长——这是长上下文最大的隐性成本。

**KV 每 token 开销公式：**

```
KV/token = 2 × 层数 × KV头数 × head_dim × 每元素字节数
```

以 GQA 架构为算例（48 层、8 个 KV 头、head_dim 128）。这是用于解释公式的假设参数，不代表已核实实际 27B 模型配置；使用时应代入所用模型 `config.json` 的实际值。

公式中的 2 表示 K 和 V；FP16 每元素 2 bytes，理想打包的 4-bit 每元素 0.5 bytes。以下按单条序列、所有层缓存全部 token、K/V 使用相同位宽计算：

```
FP16: 2 × 48 × 8 × 128 × 2   = 196,608 bytes/token = 192 KiB/token
4-bit: 2 × 48 × 8 × 128 × 0.5 = 49,152 bytes/token  = 48 KiB/token
32K 4-bit: 49,152 × 32,768 = 1,610,612,736 bytes = 1.5 GiB
```

此处 8K / 32K / 64K 分别为 8,192 / 32,768 / 65,536 tokens，包含已缓存的输入与生成 token。1 KiB = 1,024 bytes，1 GiB = 1,073,741,824 bytes；GB 表示十进制 1,000,000,000 bytes，不能与 GiB 混用。其他章节中的硬件容量与权重 GB 估算不直接作为可分配的 KV 预算。

| 缓存位宽 | 每 token | 8K 上下文 | 32K 上下文 | 64K 上下文 |
|---|---|---|---|---|
| FP16 | 192 KiB | 1.5 GiB | 6 GiB | **12 GiB** |
| **4-bit（理想打包）** | **48 KiB** | **0.375 GiB** | **1.5 GiB** | **3 GiB** |

**这里是 KV 数据本体的理想容量，不是运行时实测内存。** 4-bit 相比 FP16 降至四分之一（减少 75%），不是减半。实际量化缓存还可能包含分组 scale、zero-point、对齐与分配开销；峰值总内存还包括权重、激活、临时缓冲及运行时开销。并发序列和保留的前缀缓存也可能增加总占用，不能把表格直接当作服务的内存上限。

**GQA（分组查询注意力）是关键。** 在层数、head_dim、缓存位宽和 token 数相同的前提下，8 个 KV 头对 48 个查询头，KV 容量是每个查询头各有一组 K/V 的 MHA 的 1/6。将 KV 头从 8 改为 48，容量增至六倍：32K 时 FP16 从 6 GiB 增至 36 GiB，理想 4-bit 从 1.5 GiB 增至 9 GiB；不是翻倍。

**64K 是否可行，需要运行时验证：**
- 本算例的 64K 理想 4-bit KV 为 3 GiB，是 32K 的两倍
- 还需计入量化元数据、峰值激活、临时缓冲、分配碎片及实际 Metal/wired 限制
- 仅凭 KV 公式，既不能断言 64K 必然 OOM，也不能确认 64K 已可运行；需记录实际模型配置、运行时版本、缓存格式、并发数，以及 prefill 和 decode 的峰值内存与错误日志
- 因此保留本文当前的 32K 保护性配置；它不是由此公式证明的硬件极限，64K 的稳定性仍待验证


## 3. 为什么 KV 表格不能证明服务可用

假设上面的 32K 理想 KV 为 1.5 GiB，也不能直接用“48GB 减权重”得到可用上下文。这里既混用了容量单位，也漏掉了运行期间的其他分配。系统显示的剩余内存同样不能代替运行时的分配记录。

遇到 OOM，应先保存失败请求、实际配置和原始错误，再逐次减少输入长度或并发，观察失败边界。一次只改一个条件；不要同时改缓存位宽、上下文和系统内存限制，否则即使运行恢复，也无法知道哪个变化起作用。

旧稿使用的 32K 是配置讨论中的保护性上限，**不是已证明的硬件极限**。关于工具链要求主模型达到 64K、修改配置必须重启等描述，缺少对应软件版本与配置快照，不应作为通用规则。应以实际服务读取的配置和官方版本说明为准。

## 4. 一份有用的运行记录至少包含什么

| 记录 | 用途 |
| --- | --- |
| 芯片型号、系统、模型仓库与固定版本、量化格式、运行时版本 | 让别人知道测试对象是否相同 |
| 输入 token 数、生成 token 数、并发、缓存冷热状态 | 避免拿不同工作量比较速度 |
| 加载、prefill、decode 的峰值内存 | 区分权重预算与运行峰值 |
| 首 token 延迟、生成耗时、失败请求与原始日志 | 不只保留成功样本 |
| 相同任务下的输出与评分方法 | 判断省内存是否牺牲了需要的质量 |

这是一份待补齐的记录清单，不是已完成实验。若服务不暴露某个指标，就标成未知；不要把进程总耗时当作纯 decode 时间，也不要把缺失的内存数据写成零。

<details><summary>小练习：只把上下文从 32K 增至 64K，会发生什么？</summary>

在本文假设下，理想 4-bit KV 数据量从 1.5 GiB 增至 3 GiB。权重本身不会因此翻倍；峰值总内存也未必恰好翻倍。能否运行和是否更快，都需要同条件测量。
