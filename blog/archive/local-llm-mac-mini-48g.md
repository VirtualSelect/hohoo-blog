在 48GB 统一内存的 Mac mini 上跑 27B 量级的本地模型，成本最低，坑也最多。这篇记录的不是"能跑通"，而是**为什么这样配、为什么那样会崩**——把量化、KV 缓存、统一内存三个子系统拆到参数级。

## 结论速览

| 决策点 | 结论 | 原因 |
|---|---|---|
| 模型规模 | 27B Q4 | 权重约 16GB；剩余内存还需覆盖系统、KV、激活与运行时开销 |
| 量化方案 | oQ4 类 4-bit（含异常值通道） | 纯 4-bit 在长文本质量上劣化，异常值通道是折中 |
| KV 缓存 | 4-bit | 理想 KV 数据量为 FP16 的 1/4，实际还含量化与分配开销 |
| 上下文 | 32K 封顶 | 当前保护性配置；64K 稳定性待实测 |
| MTP | 开启 | 多 token 预测头，花 ~2GB 换 30%+ 吞吐 |
| 定位 | 辅助/回退模型 | 当前 32K 配置不满足本文工具链的 64K 主模型门槛 |

## 1. 模型选型：27B 是甜点，但“Q4”不是一回事

**权重内存的构成**（以 4-bit + 异常值通道 + MTP 方案为例）：

```
总权重 ≈ 主干参数(4-bit) + Embedding(通常保持 16-bit) + MTP 头(4-bit) + 输出头(16-bit)
```

27B 参数若全部压到 4-bit：27B × 0.5B ≈ 13.5GB。但工程上不会这么干——Embedding 和输出头对精度敏感，通常保持高位，主干里也会有少量异常值通道保持高位。最终落到 16GB 左右，是"可用精度"和"内存预算"的平衡点。

**量化方案对比：**

| 方案 | 权重占用 | 精度 | 速度 | 结论 |
|---|---|---|---|---|
| FP16 | ~54GB | 基准 | 最慢 | 48GB 机器不可行 |
| INT8 | ~27GB | 几乎无损 | 中 | 上下文预算被压缩 |
| 纯 4-bit（NF4 类） | ~16GB | 长文本偶发质量劣化 | 快 | 可用但不够稳 |
| **4-bit + 异常值通道（oQ4 类）** | **~16GB** | **接近 8-bit** | **快** | **推荐** |

4-bit 的核心矛盾：权重矩阵里存在少量"异常值"通道，数值幅度远大于其他通道，一刀切压 4-bit 会让这些通道量化误差爆炸。oQ4 类方案的思路是把这些通道单独识别出来保持高位——代价是几个百分比的额外内存，换来长文本质量的明显稳定。

**MTP（多 token 预测）头**：不是"预测下一个词"，而是并行预测未来若干个 token，再用小模型逐级校验接受。吞吐提升通常 30–50%，代价是一份小头参数 + 校验计算，总内存开销约 2GB。对 48GB 机器，这笔交易值得做。

## 2. KV 缓存：上下文真正的成本中心

自回归生成时，每个 token 的注意力 Key/Value 都要缓存，KV 缓存随上下文**线性**增长——这是长上下文最大的隐性成本。

**KV 每 token 开销公式：**

```
KV/token = 2 × 层数 × KV头数 × head_dim × 每元素字节数
```

以 GQA 架构为算例（48 层、8 个 KV 头、head_dim 128）。这是用于解释公式的假设参数，不代表已核实实际 27B 模型配置；使用时应代入所用模型 `config.json` 的实际值。

公式中的 2 表示 K 和 V；FP16 每元素 2 bytes，理想打包的 4-bit 每元素 0.5 bytes。以下按单条序列、所有层缓存全部 token、K/V 使用相同位宽计算：

```
FP16: 2 × 48 × 8 × 128 × 2   = 196,608 bytes/token = 192 KiB/token
4-bit: 2 × 48 × 8 × 128 × 0.5 = 49,152 bytes/token  = 48 KiB/token
32K 4-bit: 49,152 × 32,768 = 1,610,612,736 bytes = 1.5 GiB
```

此处 8K / 32K / 64K 分别为 8,192 / 32,768 / 65,536 tokens，包含已缓存的输入与生成 token。1 KiB = 1,024 bytes，1 GiB = 1,073,741,824 bytes；GB 表示十进制 1,000,000,000 bytes，不能与 GiB 混用。其他章节中的硬件容量与权重 GB 估算不直接作为可分配的 KV 预算。

| 缓存位宽 | 每 token | 8K 上下文 | 32K 上下文 | 64K 上下文 |
|---|---|---|---|---|
| FP16 | 192 KiB | 1.5 GiB | 6 GiB | **12 GiB** |
| **4-bit（理想打包）** | **48 KiB** | **0.375 GiB** | **1.5 GiB** | **3 GiB** |

**这里是 KV 数据本体的理想容量，不是运行时实测内存。** 4-bit 相比 FP16 降至四分之一（减少 75%），不是减半。实际量化缓存还可能包含分组 scale、zero-point、对齐与分配开销；峰值总内存还包括权重、激活、临时缓冲及运行时开销。并发序列和保留的前缀缓存也可能增加总占用，不能把表格直接当作服务的内存上限。

**GQA（分组查询注意力）是关键。** 在层数、head_dim、缓存位宽和 token 数相同的前提下，8 个 KV 头对 48 个查询头，KV 容量是每个查询头各有一组 K/V 的 MHA 的 1/6。将 KV 头从 8 改为 48，容量增至六倍：32K 时 FP16 从 6 GiB 增至 36 GiB，理想 4-bit 从 1.5 GiB 增至 9 GiB；不是翻倍。

**64K 是否可行，需要运行时验证：**
- 本算例的 64K 理想 4-bit KV 为 3 GiB，是 32K 的两倍
- 还需计入量化元数据、峰值激活、临时缓冲、分配碎片及实际 Metal/wired 限制
- 仅凭 KV 公式，既不能断言 64K 必然 OOM，也不能确认 64K 已可运行；需记录实际模型配置、运行时版本、缓存格式、并发数，以及 prefill 和 decode 的峰值内存与错误日志
- 因此保留本文当前的 32K 保护性配置；它不是由此公式证明的硬件极限，64K 的稳定性仍待验证

**KV 4-bit 的精度代价**：小数位被压掉后，长程注意力的细微排序可能出错。本地工具场景（代码补全、摘要、问答）影响可忽略；但涉及长文档精确定位的任务，需要实测验证。这也是"先用、再验"的原因。

## 3. 统一内存：为什么“内存还有剩”也会 OOM

Apple Silicon 是**统一内存**——CPU 和 GPU 共享同一块物理内存，但被划分为不同堆区：

- **CPU 堆**：进程地址空间，权重加载、中间张量走这里
- **Metal GPU 堆**：推理计算与 KV 缓存的主战场，受 `iogpu.wired_limit_mb` 约束
- **wired 限制**：GPU 可占用的"已钉住"内存上限

关键坑：`Activity Monitor` 里显示"内存充足"不代表 GPU 堆没满。GPU 堆的可用空间由 wired 限制和已分配缓冲共同决定——**OOM 常常发生在"总内存还有富余"的时候**。

排障顺序：
1. 看日志 `gateway.error.log` 中的 `Metal OOM` 行
2. 确认 KV 位宽、上下文长度是否超过预算
3. 检查 `model_settings.json` 是否生效（改完必须重启服务——KV 缓存分配器在加载时初始化，热改无效）
4. 调整 `iogpu.wired_limit_mb` 前先确认这是"限制"而非"瓶颈"——曾提到 45219，重启后失效，说明该参数并非每次启动都持久化，需要逐次验证

## 4. 上下文长度：32768 是怎么来的

模型本身支持远大于 32K 的上下文，但本文将**服务配置**保护性封顶为 32768，需区分三类约束：

1. **内存预算**：见第 2 节，32K 理想 4-bit KV 为 1.5 GiB；实际峰值另测，不能据此推出 32K 硬上限
2. **服务端配置**：`model_settings.json` 中的上下文上限，是保护性封顶
3. **工具链门槛**：本文所用 Agent 框架主模型要求 64K 起步，32K 直接不满足，只能降级为辅助/回退

**配置层的正确姿势：按 provider 设上下文，而不是全局一个值。** 全局 `context_length` 一个值会卡死所有模型——云端大窗口模型被压小浪费预算，本地小窗口模型被拉大可能超出实际内存预算。正确做法是每个 provider 独立配置（如 xfyun 给 262144、omlx 给 32768），框架在路由时按模型能力分配任务。

**与 prompt caching 的关系**：KV 缓存同时也是 prompt caching 的载体。前缀稳定时，重复 prompt 的 KV 可以直接命中复用，省掉重复 prefill 计算。这要求请求侧保持前缀结构稳定——这也是为什么"上下文工程"（预算、卸载、压缩）和 KV 量化是同一枚硬币的两面，而非两个话题。

## 5. 排障手册

| 症状 | 排查路径 |
|---|---|
| 生成突然中断、报错 | 看 `gateway.error.log` 的 `Model fallback` 与 `Metal OOM` |
| 输出明显变慢 | 上下文接近上限时 KV 膨胀，检查 `agent.log` 每轮实际上下文 |
| 配置改了没生效 | `~/.omlx/bin/omlx restart`，确认服务重启后再测 |
| 长 prompt 直接崩 | 降上下文封顶，或临时降 KV 位宽验证 |
| 内存够却 OOM | 查 `iogpu.wired_limit_mb` 与 GPU 堆实际占用，别信系统总内存 |

## 6. 给 48GB 机器的推荐配置

| 项目 | 推荐值 | 说明 |
|---|---|---|
| 模型 | 27B Q4（4-bit + 异常值通道 + MTP） | 权重约 16GB；剩余内存还需覆盖系统、KV、激活与运行时开销 |
| 量化 | 4-bit + 异常值通道 | 精度与内存的折中 |
| KV 缓存 | 4-bit | 本算例 32K 理想 KV 从 FP16 的 6 GiB 降至 1.5 GiB |
| 上下文封顶 | 32K | 当前保护性配置；64K 需验证峰值内存和稳定性 |
| MTP | 开启 | 吞吐 30%+ 提升，成本 ~2GB |
| 配置生效 | 改完必须 restart | `model_settings.json` 热改无效 |
| 角色定位 | 辅助/回退模型 | 当前工具链要求主模型支持 64K+，32K 配置不满足 |

## 7. 总结

48GB Mac mini 跑本地 27B 模型，本质是在三个子系统之间做预算分配：

1. **量化预算**：权重压到 16GB，用异常值通道保住精度
2. **KV 预算**：本算例 4-bit + GQA 的理想 KV 在 32K 为 1.5 GiB、64K 为 3 GiB；实际占用与 OOM 风险需运行时验证
3. **内存预算**：统一内存不是无限池，GPU 堆受 wired 限制，总内存余量不足以单独判断是否会 OOM

把这套参数配好、重启生效、按 provider 设上下文后，还需用实际任务验证稳定性。若要提高到 64K，应先测量峰值内存与任务质量，再决定是否需要更多内存或云端方案。

**本地模型的意义不是替代云端，而是补上云端给不了的那一格：隐私、离线、可控。**
