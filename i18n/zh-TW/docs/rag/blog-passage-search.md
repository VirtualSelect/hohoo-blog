在v1凍結驗收輸入 `缓存 保证成功`，前五個候選中出現了一篇會話並行文章。命中的文字講的是「響應驗證成功才提交」，並沒有回答快取能否保證成功。這裡保留簡體查詢字串，因為v1驗收使用的是簡體語料，不是繁體查詢評測。

這不是頁面沒有載入，也不是來源連結失效。**檢索確實找到了文字，卻沒有找到問題所要求的依據。** 這個反例比「搜尋框能回傳結果」更能說明原型還缺什麼。

本文對應尚未上線的本地預覽：開啟全站搜尋，選擇「正文段落」。實作和驗收腳本在部落格倉庫，原有Java教學工程不受影響。AI輔助整理；問題相關性標註待作者複核。

## 「保證成功」和「驗證成功」共享了什麼

中文沒有天然的空格分詞邊界。這個輕量基線把連續漢字拆成相鄰雙字。以下程式保留驗收所用的簡體原字串：

```js
import { searchTerms } from "./apps/web/lib/section-search.mjs";
console.log(searchTerms("保证成功")); // 保证、证成、成功
console.log(searchTerms("验证成功")); // 验证、证成、成功
```

兩組共享「证成」和「成功」。查詢允許部分詞項匹配，因此即使候選沒有談到快取，也可能獲得分數。「证成」在這裡還是跨詞邊界產生的字元組合，並不是想檢索的概念。

排序使用詞頻、詞項在語料中的普遍程度與段落長度；文章標題只提供較低權重，正文或小節標題必須實際命中。這些規則能排出一個順序，不能理解「保證」的斷言，也不能判斷段落是否支持它。直接給第一名貼上「答案」或把分數轉成「可信度」，都會誇大詞彙匹配的能力。

## 先確保每段話都能回到原文

段落來自本站已發表的教學與隨筆。建構器讀取清理後的文章HTML，沿用頁面實際使用的二級、三級標題錨點，不另造一套標題ID。較短的相鄰段落在同一小節內合併；單塊最多900字元。程式碼區塊、表格、資訊、計畫與缺失語言的回退正文不進入索引。

為什麼合併？單獨檢索到「讀取逾時90秒」容易丟掉後面那句「不是整個請求的總時限」。合併能保留一些相鄰解釋，但900字元上限仍可能切斷更長的論證。它是有邊界的取捨，不保證所有答案都完整落在一個區塊。

本機複查還發現了一種實際遺失：快取文章的折疊練習原題是「864 行降到 432 行，能否說快了 50%？」，舊擷取器只取`p/li`，跳過`summary`，卻把解答「不能」接到前一段後面。即使引用文字來自原文，這樣的摘錄仍缺少回答對象。

現在由既有HTML解析器保留「原題＋解答」，與折疊區外的文字分開；長解答需要分塊時，每塊重複原題，連同原題最多900字元。搜尋結果單列原題，複製引用也包含它。這裡修正的是擷取邊界，沒有改寫原題、生成新答案或證明檢索已經能理解否定。原v1語料與成績保留，目前索引另做回歸。

早期原型用陣列位置產生段落編號：前面增加文章，後面的編號就會改變。現在用以下輸入產生內容相關的識別碼：

```text
段落ID = 文件ID + SHA-256(原文小節位址 + 換行 + 完整段落)的前20位
內容指紋 = SHA-256(完整段落)
```

增加無關文章不再改變這個ID；修改段落會產生新ID。**位置與文字一致性不等於事實正確性**，指紋只回答「是不是這一版摘錄」。

## 複製引用時，保留完整段落與版本

結果清單只顯示短摘錄；「複製引用」保留完整段落、文章與小節、正式來源位址、帶雜湊的索引快照位址及完整內容指紋。複製失敗時顯示可選取的文字，不把失敗偽裝成「已複製」。

來源連結方便繼續閱讀，指紋便於核對文字有沒有變化。但索引快照不是永久存檔：舊雜湊資源可能在後續部署清理，文章也可能修訂。需要長期使用時應保留引用文字與指紋。目前預覽未發佈，相應的線上快照位址尚不可存取。

瀏覽器只在切換到正文模式時載入目前語言索引；問題不傳送給模型，也不會上傳第三方。英文與繁體使用各自正文，缺少翻譯時不悄悄混入簡體中文。

## 在固定版本重現驗收

以下指令在**本次預覽工程的倉庫根目錄**執行。目前線上主幹尚未包含這些檔案，需先取得對應改動。依賴已安裝時跳過第一行：

```powershell
npm ci --prefix apps/web
npm run prepare:content --prefix apps/web
npm run search:evaluate --prefix apps/web
```

執行環境為Windows、Node.js 26.8.2。輸出檔案是 `reports/section-search-evaluation-v1.json`，包含每個問題的原始候選、相關依據、排名與內容指紋。

協議位於`apps/web/tests/fixtures/section-search-protocol.json`，快照為同目錄的`section-search-snapshot.json`。原始513塊文字保存在`section-search-corpus-v1.json`，已核對到原語料指紋；後續正文修訂不覆蓋這份測試語料。預設命令重跑原問題、演算法與凍結語料，版本不符便停止，不能靜默沿用舊結論。本篇仍被排除，避免把解釋驗收問題的文章重新當成證據。

檢查目前正文可另執行`node apps/web/scripts/evaluate-section-search.mjs --live`，輸出`reports/section-search-evaluation-current.json`。它沿用相同開發問題、使用目前語料，是開發回歸，不是新的獨立評測，亦不覆蓋v1。測試語料不進入網站公開索引或瀏覽器腳本。

找不到索引時先執行內容產生；出現快照不一致時先檢查原始碼、問題與語料版本。不要為了測試通過而覆蓋v1快照。新條件應使用新版本協議，保留舊記錄。

## 這12個問題實際說明了什麼

凍結語料包含61篇教學與隨筆、513個段落區塊。8個問題指定相關小節與必須出現的原文引句；另外4個問題標為沒有可支持的答案。標籤由AI整理，尚未經過作者獨立複核。

實際執行時，8個有依據的問題均在前5個候選中找到指定段落，且都排第一。這個結果並不意外：查詢刻意貼近原文詞彙，演算法也已用其他開發範例調整過。它只說明這些工程驗收條件成立，**不能當作真實讀者問題的準確率，更不是獨立保留集成績**。

4個無答案問題中，3個回傳空清單；`缓存 保证成功` 仍回傳5個候選。原始記錄保留這次誤命中，沒有提高閾值後重新挑選好看的結果。檢索器回傳候選本身不是生成錯誤回答；它暴露的是：後續問答層不能把「有候選」當作「有足夠依據」。

## 自己改出一個反例

先不要調閾值。在本次預覽倉庫根目錄，貼上下面整個PowerShell程式碼區塊執行；它只讀取v1凍結協議與語料，不需要安裝模型或產生索引，也不會覆寫驗收報告。查詢從協議讀取，避免手動改寫原問題。這裡使用簡體歷史語料，不保證與目前語言的線上搜尋結果相同。

```powershell
@'
import fs from "node:fs";
import { searchTerms, createSectionSearcher } from "./apps/web/lib/section-search.mjs";
const root = "apps/web/tests/fixtures/";
const read = (name) => JSON.parse(fs.readFileSync(root + name, "utf8"));
const protocol = read("section-search-protocol.json");
const corpus = read("section-search-corpus-v1.json");
const query = protocol.questions.find((q) => q.id === "absent-guarantee").query;
const queryTerms = [...new Set(searchTerms(query))];
const results = createSectionSearcher(corpus)(query, protocol.topK);
console.log(JSON.stringify({
  query,
  queryTerms,
  firstTwo: results.slice(0, 2).map((p) => {
    const present = new Set(searchTerms(p.heading + " " + p.text));
    return {
      id: p.id,
      href: p.href,
      matched: queryTerms.filter((term) => present.has(term)),
      missing: queryTerms.filter((term) => !present.has(term)),
    };
  }),
}, null, 2));
'@ | node --input-type=module
```

預期`queryTerms`是`缓存、保证、证成、成功`，前兩個候選保留以下差異：

| 凍結候選 | 小節標題或正文中重合的詞項 |
| --- | --- |
| [會話並行文章開頭](/docs/ai-apps/java-concurrent-history) | 证成、成功 |
| [滑動快取的三個索引](/docs/llm/sliding-cache-positions#5-三個索引不要擠成一個變量) | 缓存、保证 |

第一行的「響應驗證成功才提交」在談會話提交，不是在談快取。第二行的「不保證其他架構具有相同性質」是在限定範圍，不能刪去「不」或換成成功保證。

這兩行都有兩個詞項重合，第二行甚至有「缓存」，仍不能支持原問題。`matched`只計算查詢與小節標題/正文的詞項交集，不是評分公式的逐項貢獻，也不包含文章標題；標題加權、詞頻與長度仍會影響名次。**缺詞可以提醒你檢查，詞齊全也不能替你判斷語義。**

自檢時先說清每條原句允許得出的結論，再寫一句它不能支持的擴大說法。若程式沒有輸出預期差異，先確認目前目錄、凍結檔案與演算法指紋；別用目前索引替換舊語料。

若要求查詢詞全部齊全，這兩條都會被刪掉，但規則仍不能識別否定。可以構造一個教學句子：`缓存不能保证成功。`（快取不能保證成功。）它含有全部四個簡體查詢詞，含義卻是否定保證。這句只用於檢查推理，不加入v1語料或成績。

先在正文搜尋試一組原文關鍵字，再換成相同意思、不同用詞的問題。比較回傳的小節，而不是只數結果；這是探索，不納入v1成績。接著選一條引用，刪掉限定條件，觀察同一段文字為什麼可能支持局部判斷，卻不能支持擴大後的說法。

若要研究分塊，應先獨立標註哪些段落真正支持問題，再凍結問題、分詞器與檢索器，只改變分塊方式。問答還需要回答生成、資料不足時的處理與引用支持驗收。這些仍是[RAG後續路線](/learning?track=rag)中的計畫。

可以先讀[檢索證據驗收](/docs/ai-apps/java-retrieval-evidence)，再看[引用真實但聲明錯誤](/docs/ai-apps/java-grounded-claims)。這次原型把資料換成真實部落格正文，並沒有完成向量檢索、語義重排或完整RAG產品。
