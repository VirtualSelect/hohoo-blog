在 48GB 統一記憶體裡，模型權重、KV 快取和執行時暫存配置要共用同一份預算。只知道「27B、4-bit」，還不足以判斷某個上下文長度能否穩定執行。

**閱讀範圍（2026-11-07 複核）：本文保留容量推導與配置討論，不作為部署效能實測報告。** 目前倉庫沒有與本文配套的完整模型識別、晶片型號、執行時版本、同條件吞吐紀錄及 OOM 日誌，無法據此推薦特定量化套件或確認 MTP 效益。原稿的「約 2GB 換 30%–50% 吞吐」「量化後幾乎無損」等斷言撤回。

## 1. 先算能算的，再測不能算的

27B 參數全部以 FP16 儲存時，僅參數資料的理想容量為 27 × 10⁹ × 2 = **54GB**；全部按 4-bit 緊湊儲存則為 **13.5GB**。兩者都不是實際載入後的程序記憶體。

模型套件可能混用不同精度，並帶有量化中繼資料。實際預算還包括系統、激活、快取和暫存緩衝區。先記錄模型版本與量化格式，再測載入後的佔用，比從檔名裡的「Q4」推斷速度或品質可靠。

| 問題 | 可以先推導什麼 | 必須補測什麼 |
| --- | --- | --- |
| 權重能否裝下 | 參數數 × 位寬的理想容量 | 實際模型套件與載入峰值 |
| 上下文能開多長 | 由實際模型配置計算 KV 資料量 | prefill / decode 峰值、並行與錯誤日誌 |
| 量化是否值得 | 理想儲存量變化 | 同題回答品質、延遲與實際記憶體 |
| MTP 是否開啟 | 先確認模型與執行時是否支援 | 同輸入、同輸出長度的開關對照 |

MTP 的效益和記憶體代價不能從模型總參數量推出。本文沒有這組對照，因此不給預設開啟建議。

## 2. KV 快取：上下文真正的成本中心

自回歸生成時，每個 token 的注意力 Key/Value 都要快取，KV 快取隨上下文**線性**增長——這是長上下文最大的隱性成本。

**KV 每 token 開銷公式：**

```
KV/token = 2 × 層數 × KV頭數 × head_dim × 每元素位元組數
```

以 GQA 架構為算例（48 層、8 個 KV 頭、head_dim 128）。這是用於解釋公式的假設參數，不代表已核實實際 27B 模型配置；使用時應代入所用模型 `config.json` 的實際值。

公式中的 2 表示 K 和 V；FP16 每元素 2 bytes，理想打包的 4-bit 每元素 0.5 bytes。以下按單條序列、所有層快取全部 token、K/V 使用相同位寬計算：

```
FP16: 2 × 48 × 8 × 128 × 2   = 196,608 bytes/token = 192 KiB/token
4-bit: 2 × 48 × 8 × 128 × 0.5 = 49,152 bytes/token  = 48 KiB/token
32K 4-bit: 49,152 × 32,768 = 1,610,612,736 bytes = 1.5 GiB
```

此處 8K / 32K / 64K 分別為 8,192 / 32,768 / 65,536 tokens，包含已快取的輸入與生成 token。1 KiB = 1,024 bytes，1 GiB = 1,073,741,824 bytes；GB 表示十進位 1,000,000,000 bytes，不能與 GiB 混用。其他章節中的硬體容量與權重 GB 估算不直接作為可分配的 KV 預算。

| 快取位寬 | 每 token | 8K 上下文 | 32K 上下文 | 64K 上下文 |
|---|---|---|---|---|
| FP16 | 192 KiB | 1.5 GiB | 6 GiB | **12 GiB** |
| **4-bit（理想打包）** | **48 KiB** | **0.375 GiB** | **1.5 GiB** | **3 GiB** |

**這裡是 KV 資料本體的理想容量，不是執行時實測記憶體。** 4-bit 相比 FP16 降至四分之一（減少 75%），不是減半。實際量化快取還可能包含分組 scale、zero-point、對齊與分配開銷；峰值總記憶體還包括權重、激活、臨時緩衝及執行時開銷。並行序列和保留的前綴快取也可能增加總佔用，不能把表格直接當作服務的記憶體上限。

**GQA（分組查詢注意力）是關鍵。** 在層數、head_dim、快取位寬和 token 數相同的前提下，8 個 KV 頭對 48 個查詢頭，KV 容量是每個查詢頭各有一組 K/V 的 MHA 的 1/6。將 KV 頭從 8 改為 48，容量增至六倍：32K 時 FP16 從 6 GiB 增至 36 GiB，理想 4-bit 從 1.5 GiB 增至 9 GiB；不是翻倍。

**64K 是否可行，需要執行時驗證：**
- 本算例的 64K 理想 4-bit KV 為 3 GiB，是 32K 的兩倍
- 還需計入量化中繼資料、峰值激活、臨時緩衝、分配碎片及實際 Metal/wired 限制
- 僅憑 KV 公式，既不能斷言 64K 必然 OOM，也不能確認 64K 已可執行；需記錄實際模型配置、執行時版本、快取格式、並行數，以及 prefill 和 decode 的峰值記憶體與錯誤日誌
- 因此保留本文目前的 32K 保護性配置；它不是由此公式證明的硬體極限，64K 的穩定性仍待驗證


## 3. 為什麼 KV 表格不能證明服務可用

假設上面的 32K 理想 KV 為 1.5 GiB，也不能直接用「48GB 減權重」得到可用上下文。這裡既混用了容量單位，也漏掉了執行期間的其他配置。系統顯示的剩餘記憶體同樣不能代替執行時的配置紀錄。

遇到 OOM，先保存失敗請求、實際配置和原始錯誤，再逐次減少輸入長度或並行數，觀察失敗邊界。一次只改一個條件；不要同時改快取位寬、上下文和系統記憶體限制，否則即使執行恢復，也無法知道哪個變化起作用。

舊稿使用的 32K 是配置討論中的保護性上限，**不是已證明的硬體極限**。關於工具鏈要求主模型達到 64K、修改配置必須重啟等描述，缺少對應軟體版本與配置快照，不應作為通用規則。應以實際服務讀取的配置和官方版本說明為準。

## 4. 一份有用的執行紀錄至少包含什麼

| 紀錄 | 用途 |
| --- | --- |
| 晶片型號、系統、模型倉庫與固定版本、量化格式、執行時版本 | 確認測試對象是否相同 |
| 輸入 token 數、生成 token 數、並行數、快取冷熱狀態 | 比較相同工作量 |
| 載入、prefill、decode 的峰值記憶體 | 區分權重預算與執行峰值 |
| 首 token 延遲、生成耗時、失敗請求與原始日誌 | 保留失敗樣本 |
| 相同任務下的輸出與評分方法 | 判斷省記憶體是否犧牲了需要的品質 |

這是一份待補齊的紀錄清單，不是已完成實驗。若服務不提供某個指標，就標成未知；不要把程序總耗時當作純 decode 時間，也不要把缺失的記憶體資料寫成零。

<details><summary>小練習：只把上下文從 32K 增至 64K，會發生什麼？</summary>

在本文假設下，理想 4-bit KV 資料量從 1.5 GiB 增至 3 GiB。權重本身不會因此翻倍；峰值總記憶體也未必恰好翻倍。能否執行和是否更快，都需要同條件測量。
