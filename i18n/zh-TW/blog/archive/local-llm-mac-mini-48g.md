在 48GB 統一記憶體的 Mac mini 上跑 27B 量級的本地模型，成本最低，坑也最多。這篇記錄的不是「能跑通」，而是**為什麼這樣配、為什麼那樣會崩**——把量化、KV 快取、統一記憶體三個子系統拆到參數級。

## 結論速覽

| 決策點 | 結論 | 原因 |
|---|---|---|
| 模型規模 | 27B Q4 | 權重約 16GB；剩餘記憶體還需涵蓋系統、KV、激活與執行時開銷 |
| 量化方案 | oQ4 類 4-bit（含異常值通道） | 純 4-bit 在長文本質量上劣化，異常值通道是折衷 |
| KV 快取 | 4-bit | 理想 KV 資料量為 FP16 的 1/4，實際還含量化與分配開銷 |
| 上下文 | 32K 封頂 | 目前保護性配置；64K 穩定性待實測 |
| MTP | 開啟 | 多 token 預測頭，花 ~2GB 換 30%+ 吞吐 |
| 定位 | 輔助／回退模型 | 目前 32K 配置不滿足本文工具鏈的 64K 主模型門檻 |

## 1. 模型選型：27B 是甜點，但「Q4」不是一回事

**權重記憶體的構成**（以 4-bit + 異常值通道 + MTP 方案為例）：

```
總權重 ≈ 主幹參數(4-bit) + Embedding(通常保持 16-bit) + MTP 頭(4-bit) + 輸出頭(16-bit)
```

27B 參數若全部壓到 4-bit：27B × 0.5B ≈ 13.5GB。但工程上不會這麼幹——Embedding 和輸出頭對精度敏感，通常保持高位，主幹裡也會有少量異常值通道保持高位。最終落到 16GB 左右，是「可用精度」和「記憶體預算」的平衡點。

**量化方案對比：**

| 方案 | 權重佔用 | 精度 | 速度 | 結論 |
|---|---|---|---|---|
| FP16 | ~54GB | 基準 | 最慢 | 48GB 機器不可行 |
| INT8 | ~27GB | 幾乎無損 | 中 | 上下文預算被壓縮 |
| 純 4-bit（NF4 類） | ~16GB | 長文本偶發質量劣化 | 快 | 可用但不夠穩 |
| **4-bit + 異常值通道（oQ4 類）** | **~16GB** | **接近 8-bit** | **快** | **推薦** |

4-bit 的核心矛盾：權重矩陣裡存在少量「異常值」通道，數值幅度遠大於其他通道，一刀切壓 4-bit 會讓這些通道量化誤差爆炸。oQ4 類方案的思路是把這些通道單獨識別出來保持高位——代價是幾個百分比的額外記憶體，換來長文本質量的明顯穩定。

**MTP（多 token 預測）頭**：不是「預測下一個詞」，而是並行預測未來若干個 token，再用小模型逐級校驗接受。吞吐提升通常 30–50%，代價是一份小頭參數 + 校驗計算，總記憶體開銷約 2GB。對 48GB 機器，這筆交易值得做。

## 2. KV 快取：上下文真正的成本中心

自回歸生成時，每個 token 的注意力 Key/Value 都要快取，KV 快取隨上下文**線性**增長——這是長上下文最大的隱性成本。

**KV 每 token 開銷公式：**

```
KV/token = 2 × 層數 × KV頭數 × head_dim × 每元素位元組數
```

以 GQA 架構為算例（48 層、8 個 KV 頭、head_dim 128）。這是用於解釋公式的假設參數，不代表已核實實際 27B 模型配置；使用時應代入所用模型 `config.json` 的實際值。

公式中的 2 表示 K 和 V；FP16 每元素 2 bytes，理想打包的 4-bit 每元素 0.5 bytes。以下按單條序列、所有層快取全部 token、K/V 使用相同位寬計算：

```
FP16: 2 × 48 × 8 × 128 × 2   = 196,608 bytes/token = 192 KiB/token
4-bit: 2 × 48 × 8 × 128 × 0.5 = 49,152 bytes/token  = 48 KiB/token
32K 4-bit: 49,152 × 32,768 = 1,610,612,736 bytes = 1.5 GiB
```

此處 8K / 32K / 64K 分別為 8,192 / 32,768 / 65,536 tokens，包含已快取的輸入與生成 token。1 KiB = 1,024 bytes，1 GiB = 1,073,741,824 bytes；GB 表示十進位 1,000,000,000 bytes，不能與 GiB 混用。其他章節中的硬體容量與權重 GB 估算不直接作為可分配的 KV 預算。

| 快取位寬 | 每 token | 8K 上下文 | 32K 上下文 | 64K 上下文 |
|---|---|---|---|---|
| FP16 | 192 KiB | 1.5 GiB | 6 GiB | **12 GiB** |
| **4-bit（理想打包）** | **48 KiB** | **0.375 GiB** | **1.5 GiB** | **3 GiB** |

**這裡是 KV 資料本體的理想容量，不是執行時實測記憶體。** 4-bit 相比 FP16 降至四分之一（減少 75%），不是減半。實際量化快取還可能包含分組 scale、zero-point、對齊與分配開銷；峰值總記憶體還包括權重、激活、臨時緩衝及執行時開銷。並行序列和保留的前綴快取也可能增加總佔用，不能把表格直接當作服務的記憶體上限。

**GQA（分組查詢注意力）是關鍵。** 在層數、head_dim、快取位寬和 token 數相同的前提下，8 個 KV 頭對 48 個查詢頭，KV 容量是每個查詢頭各有一組 K/V 的 MHA 的 1/6。將 KV 頭從 8 改為 48，容量增至六倍：32K 時 FP16 從 6 GiB 增至 36 GiB，理想 4-bit 從 1.5 GiB 增至 9 GiB；不是翻倍。

**64K 是否可行，需要執行時驗證：**
- 本算例的 64K 理想 4-bit KV 為 3 GiB，是 32K 的兩倍
- 還需計入量化中繼資料、峰值激活、臨時緩衝、分配碎片及實際 Metal/wired 限制
- 僅憑 KV 公式，既不能斷言 64K 必然 OOM，也不能確認 64K 已可執行；需記錄實際模型配置、執行時版本、快取格式、並行數，以及 prefill 和 decode 的峰值記憶體與錯誤日誌
- 因此保留本文目前的 32K 保護性配置；它不是由此公式證明的硬體極限，64K 的穩定性仍待驗證

**KV 4-bit 的精度代價**：小數位被壓掉後，長程注意力的細微排序可能出錯。本地工具場景（代碼補全、摘要、問答）影響可忽略；但涉及長文檔精確定位的任務，需要實測驗證。這也是「先用、再驗」的原因。

## 3. 統一記憶體：為什麼「記憶體還有剩」也會 OOM

Apple Silicon 是**統一記憶體**——CPU 和 GPU 共享同一塊物理記憶體，但被劃分為不同堆區：

- **CPU 堆**：進程位址空間，權重加載、中間張量走這裡
- **Metal GPU 堆**：推理計算與 KV 快取的主戰場，受 `iogpu.wired_limit_mb` 約束
- **wired 限制**：GPU 可佔用的「已釘住」記憶體上限

關鍵坑：`Activity Monitor` 裡顯示「記憶體充足」不代表 GPU 堆沒滿。GPU 堆的可用空間由 wired 限制和已分配緩衝共同決定——**OOM 常常發生在「總記憶體還有富餘」的時候**。

排障順序：
1. 看日誌 `gateway.error.log` 中的 `Metal OOM` 行
2. 確認 KV 位寬、上下文長度是否超過預算
3. 檢查 `model_settings.json` 是否生效（改完必須重啟服務——KV 快取分配器在加載時初始化，熱改無效）
4. 調整 `iogpu.wired_limit_mb` 前先確認這是「限制」而非「瓶頸」——曾提到 45219，重啟後失效，說明該參數並非每次啟動都持久化，需要逐次驗證

## 4. 上下文長度：32768 是怎麼來的

模型本身支援遠大於 32K 的上下文，但本文將**服務配置**保護性封頂為 32768，需區分三類約束：

1. **記憶體預算**：見第 2 節，32K 理想 4-bit KV 為 1.5 GiB；實際峰值另測，不能據此推出 32K 硬上限
2. **服務端配置**：`model_settings.json` 中的上下文上限，是保護性封頂
3. **工具鏈門檻**：本文所用 Agent 框架主模型要求 64K 起步，32K 直接不滿足，只能降級為輔助／回退

**配置層的正確姿勢：按 provider 設上下文，而不是全域一個值。** 全域 `context_length` 一個值會卡死所有模型——雲端大視窗模型被壓小浪費預算，本地小視窗模型被拉大可能超出實際記憶體預算。正確做法是每個 provider 獨立配置（如 xfyun 給 262144、omlx 給 32768），框架在路由時按模型能力分配任務。

**與 prompt caching 的關係**：KV 快取同時也是 prompt caching 的載體。前綴穩定時，重複 prompt 的 KV 可以直接命中複用，省掉重複 prefill 計算。這要求請求側保持前綴結構穩定——這也是為什麼「上下文工程」（預算、卸載、壓縮）和 KV 量化是同一枚硬幣的兩面，而非兩個話題。

---

## 5. 排障手冊

| 症狀 | 排查路徑 |
|---|---|
| 生成突然中斷、報錯 | 看 `gateway.error.log` 的 `Model fallback` 與 `Metal OOM` |
| 輸出明顯變慢 | 上下文接近上限時 KV 膨脹，檢查 `agent.log` 每輪實際上下文 |
| 配置改了沒生效 | `~/.omlx/bin/omlx restart`，確認服務重啟後再測 |
| 長 prompt 直接崩 | 降上下文封頂，或臨時降 KV 位寬驗證 |
| 記憶體夠卻 OOM | 查 `iogpu.wired_limit_mb` 與 GPU 堆實際佔用，別信系統總記憶體 |

## 6. 給 48GB 機器的推薦配置

| 項目 | 推薦值 | 說明 |
|---|---|---|
| 模型 | 27B Q4（4-bit + 異常值通道 + MTP） | 權重約 16GB；剩餘記憶體還需涵蓋系統、KV、激活與執行時開銷 |
| 量化 | 4-bit + 異常值通道 | 精度與記憶體的折衷 |
| KV 快取 | 4-bit | 本算例 32K 理想 KV 從 FP16 的 6 GiB 降至 1.5 GiB |
| 上下文封頂 | 32K | 目前保護性配置；64K 需驗證峰值記憶體和穩定性 |
| MTP | 開啟 | 吞吐 30%+ 提升，成本 ~2GB |
| 配置生效 | 改完必須 restart | `model_settings.json` 熱改無效 |
| 角色定位 | 輔助／回退模型 | 目前工具鏈要求主模型支援 64K+，32K 配置不滿足 |

## 7. 總結

48GB Mac mini 跑本地 27B 模型，本質是在三個子系統之間做預算分配：

1. **量化預算**：權重壓到 16GB，用異常值通道保住精度
2. **KV 預算**：本算例 4-bit + GQA 的理想 KV 在 32K 為 1.5 GiB、64K 為 3 GiB；實際佔用與 OOM 風險需執行時驗證
3. **記憶體預算**：統一記憶體不是無限池，GPU 堆受 wired 限制，總記憶體餘量不足以單獨判斷是否會 OOM

把這套參數配好、重啟生效、按 provider 設上下文後，還需用實際任務驗證穩定性。若要提高到 64K，應先測量峰值記憶體與任務品質，再決定是否需要更多記憶體或雲端方案。

**本地模型的意義不是替代雲端，而是補上雲端給不了的那一格：隱私、離線、可控。**
